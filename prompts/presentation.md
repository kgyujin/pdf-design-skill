1. 발표자료 구성
전체 분량은 목표 슬라이드 수에 맞춰줘. 부록 슬라이드는 목표 수에 포함하지 않고 별도로 표시해줘(`slide appendix`).
원본 자료의 논리와 전개 순서를 최대한 충실하게 반영해줘.
기본 전개는 문제 또는 목적 → 필요한 배경지식 → 핵심 아이디어 → 구체적인 방법·시스템·과정 → 수식 또는 분석 → 결과와 근거 → 한계와 함의 순서로 해줘.
원본 자료의 성격상 맞지 않는 단계는 억지로 넣지 말고 자연스럽게 조정해줘.
각 슬라이드는 하나의 핵심 메시지만 전달하고, 제목(`.slide-title`)은 결론을 담은 문장으로 써줘. 제목만 순서대로 읽어도 발표 흐름이 이해되어야 해.
원본의 중요한 Figure, Chart, Table, Diagram, Algorithm, 수식, 사례는 빠뜨리지 마.
원본에 있는 내용과 수치만 정확히 사용하고, 자료에 없는 주장이나 수치를 만들지 마.
제작자의 해석이나 추가 설명은 `.interp` 박스에 넣어 원본의 주장과 구분해줘.
시각자료에는 "이 자료에서 무엇을 봐야 하는지"를 번호 설명(`.callouts`, `.pin`)이나 `.look` 문장으로 짧게 적어줘.
수식은 결과만 넣지 말고 기호 설명(`.symbols`)을 함께 넣고, 유도 과정은 대본이나 부록(`.derive`)에 넣어줘.
Algorithm이나 절차는 원문만 붙이지 말고 단계 흐름(`.l-steps`)으로 보여줘.
원본에 수식이나 Algorithm이 없으면 억지로 추가하지 마.
발표 시간 안에 설명하기 어려운 부가 내용은 대본이나 부록으로 분리해줘.

2. 레이아웃
페이지마다 같은 구성을 반복하지 말고 내용에 맞는 레이아웃을 골라줘.
- 핵심 포인트 3~5개: `l-points`
- Figure 중심: `l-figure` (필요하면 `wide`, `flip`)
- 수식 중심: `l-equation`
- 과정·Algorithm: `l-steps` (단계가 많으면 `steps vertical`)
- 비교: `l-compare` + `.verdict`
- 표: `l-table` (핵심 행은 `tr.hl`)
- 글과 시각자료 나란히: `l-split`
- 파트 구분: `slide section`
Figure는 너무 작아지지 않게 하고, Figure와 설명문의 비율을 균형 있게 맞춰줘.
본문이 너무 비어 보이지 않게 하되 긴 문단은 넣지 마. 한 장에 핵심 설명은 3~5개로 하고, 나머지는 대본으로 옮겨줘.
하나의 큰 Figure나 수식이 핵심인 슬라이드는 설명 개수를 억지로 채우지 않아도 돼.
모든 슬라이드 하단 `.source`에 원본 자료의 페이지, Figure 번호 또는 출처를 적어줘. 쪽번호는 자동으로 매겨지니 비워 둬.

3. 디자인과 글꼴
화면 비율은 16:9, 배경은 흰색, 흑백 중심의 미니멀 디자인을 기본으로 해줘(`academic` + `graphite`).
강조 색상은 원본 Figure나 Chart를 이해하는 데 필요한 곳에만 제한적으로 써줘. 색은 `var(--accent)` 같은 토큰으로만 지정해줘.
그라데이션, 장식용 아이콘, 화려한 도형, 불필요한 배경 이미지는 쓰지 마.
AI가 만든 티가 나는 패턴도 쓰지 마: 모든 제목 위의 영문 대문자 라벨, `01` 같은 0 붙은 번호, 색 채운 번호 칩, 포인트색 세로 바, 같은 모양 카드 3개 나열, 이모지, 줄표(—)로 잇는 문장. 자세한 기준은 스킬의 `references/anti-ai-design.md`를 따라줘.
참고 발표 자료가 있으면 색상, 여백, 글꼴과 분위기는 가장 가까운 스타일·색조를 고르고 `--accent`로 맞춰줘. 배치는 그대로 복사하지 마.
글꼴은 고딕(Pretendard)을 써줘. 바탕체·명조체는 내가 따로 요청할 때만 쓰고, 그때는 고운바탕(`--font serif`)으로 해줘.
글자 크기 기준은 다음과 같아(스킬 기본값). 이보다 작게 줄이지 마.
- 제목 30pt, 핵심 메시지 22pt, 본문 16~20pt, 캡션·출처 10~11pt
수식은 화면에서 바로 읽을 수 있게 크게 넣어줘(24pt 이상).
표 글자가 작아지면 한 장에 억지로 넣지 말고 여러 장으로 나누거나 핵심 행과 열만 남겨줘.
Figure의 축, 범례와 주요 숫자는 화면에서 읽을 수 있어야 해.

4. 언어
슬라이드와 대본은 상단의 언어 설정을 따라줘.
별도 설정이 없으면 슬라이드 제목과 핵심 문장은 영어, 발표 대본과 상세 설명은 한국어로 써줘.
Figure 안의 원문 표기와 고유 용어는 원래 언어를 유지해줘.
영어 전문용어가 처음 나오면 대본에서 한국어로 의미를 설명해줘.
같은 개념은 발표 전체에서 같은 용어로 불러줘.

5. 발표 대본(노트)
발표자의 배경지식이 부족해도 이해하고 발표할 수 있도록 각 슬라이드의 `aside.notes`를 작성해줘.
노트는 `h4` 소제목과 설명(`p`, `ul`, `ol`), 실제로 읽을 대본(`div.talk > p`)으로 구성해줘.
소제목은 다음 중 그 슬라이드에 필요한 것만 골라 써줘. 모든 항목을 기계적으로 넣지 마.
- 먼저 알아야 할 배경지식
- 화면에서 먼저 가리킬 부분
- Figure나 Chart를 가리키는 순서
- 축, 범례, 색상, 화살표와 박스의 의미
- 수식에 등장하는 기호의 뜻
- 수식이 만들어지는 단계별 과정
- Algorithm이나 프로세스의 입력, 반복 과정, 조건과 출력
- 헷갈리기 쉬운 점
- 이 내용이나 결과가 중요한 이유
- 다음 슬라이드 연결
대본은 원본을 번역하거나 슬라이드 문장을 그대로 읽는 형태로 쓰지 마. 화면을 가리키며 설명하는 말투로 자연스럽게 써줘.
대본 분량은 발표 시간에 맞춰줘. 중요한 Figure, 수식, Algorithm 슬라이드는 자세히, 전환·요약 슬라이드는 짧게 써줘.
`script` 명령이 대본(`div.talk`) 분량으로 발표 시간을 추정하니(한국어 분당 약 330자), 목표 시간과 ±15% 이상 차이 나면 분량을 조정해줘.

수식이 있으면 노트에서 다음 순서로 설명해줘.
- 이 수식이 무엇을 계산하거나 표현하는지
- 각 기호의 의미
- 앞 항과 뒤 항의 의미
- 출발한 기본식이나 가정
- 값을 하나씩 대입해 최종식이 나오는 과정
- 가능하면 숫자를 쓴 간단한 예시
- 이 수식이 Figure, 결과, 설계 결정과 어떻게 연결되는지

Algorithm이나 절차가 있으면 노트에서 다음 순서로 설명해줘.
- 이 알고리즘 또는 절차가 필요한 이유
- 입력값이나 시작 조건의 의미
- 각 단계나 반복문이 처리하는 대상
- 조건식이나 의사결정 기준이 필요한 이유
- 후보나 결과를 평가하는 기준
- 최종 출력값이나 도달 상태
- 가능하면 실제 숫자나 작은 사례를 쓴 예시
- 관련 Figure, 시스템 구조, 실제 결과와의 연결
수식이나 Algorithm이 없는 자료에서는 같은 원칙을 프로세스, 의사결정 구조, 분석 방법, 업무 흐름 설명에 적용해줘.

6. Figure와 시각자료
원본 자료의 Figure, Chart, Table, Diagram을 우선 사용해줘.
이미지는 `.fig-frame` 안에 넣어줘. 축, 범례, 단위, 캡션이 잘리지 않도록 crop은 최소화해줘(스킬이 `object-fit: contain`으로 비율을 유지해).
PDF에서 Figure를 추출할 때는 충분한 해상도(표시 폭의 2배 이상)로 추출해줘.
원본 시각자료가 발표에 적합하지 않으면 원저자, 기관, 기업의 공식 발표자료·보고서·문서에서 더 이해하기 쉬운 버전을 찾아 써도 돼.
외부 시각자료를 쓰면 출처를 슬라이드 하단 `.source`와 노트에 기록해줘.
복잡한 시각자료 위에 글을 많이 덮지 말고, 번호 핀(`.pin`)과 옆 설명(`.callouts`)을 써줘.
의미와 수치를 유지하면서 설명용 도식으로 다시 그려도 돼. 다시 그린 도식에는 `.fig-label`로 "adapted from" 또는 "simplified view"를 표시해줘.
설명용으로 새로 만든 그림이 원본의 실제 결과처럼 보이게 하지 마.
시각자료가 없는 내용은 긴 글 대신 관계, 순서, 비교를 보여주는 간단한 도식(SVG, `l-steps`, `l-compare`)으로 표현해줘.

7. 내용 정확성
원본의 핵심 주장, 조건, 수치와 결론을 정확하게 유지해줘.
원본에 없는 인과관계를 새로 만들지 마.
수치나 성능 결과를 제시할 때는 비교 대상, 조건, 단위, 기준을 함께 표시해줘.
특정 조건에서만 성립하는 결과를 일반적인 결론처럼 표현하지 마.
원본의 한계, 적용 조건, 반례가 있으면 함께 넣어줘.
외부 자료를 추가하면 원본 자료와 명확히 구분해줘.
내용이 불확실하거나 해석이 여러 가지면 임의로 확정하지 말고, 노트에 "주의점" 소제목으로 표시해줘.

8. 최종 검수
완성 후 다음 명령을 실행하고, 문제가 있으면 고친 뒤 다시 실행해줘.
```bash
python3 SKILL_DIR/scripts/pdfdesign.py render <deck.html> --preview --expect-pages <슬라이드 수>
python3 SKILL_DIR/scripts/pdfdesign.py check <deck.html>
python3 SKILL_DIR/scripts/pdfdesign.py script <deck.html>
```
`check`가 자동으로 확인하는 항목:
- 페이지 밖으로 넘친 요소, 본문과 하단 출처·쪽번호의 겹침, 잘린 내용
- 10pt 미만 글자, 16pt 미만 본문, 12pt 미만 표, 24pt 미만 수식, Figure 안의 작은 글자
- 불러오지 못한 이미지, 가로세로 비율이 깨진 이미지, 해상도가 낮은 이미지
- 렌더링되지 않은 수식, 수식 오류
- 발표자 노트·대본·출처·제목 누락, 5개를 넘는 핵심 포인트, 남은 자리표시 문구
- AI 티 패턴("AI 티:" 경고)

`check`로 잡을 수 없는 항목은 미리보기 PNG를 **모든 슬라이드** 열어 직접 확인해줘.
- Figure 안에서 번호 핀·라벨·데이터가 서로 가리지 않는지
- 이미지가 흐리거나 원본의 의미가 바뀌지 않았는지
- 원본의 주장과 슬라이드 수치가 일치하는지
- 원본의 핵심 Figure, 수식, Algorithm, 결과, 사례가 빠지지 않았는지
- 비슷한 내용이 여러 슬라이드에서 불필요하게 반복되지 않는지
- 대본 DOCX가 정상적으로 열리고, 슬라이드 번호가 PDF와 일치하는지(`script`가 슬라이드 순서대로 만든다)
- `script`가 추정한 발표 시간이 목표 시간 안에 드는지
문제가 발견되면 최종 파일을 전달하기 전에 먼저 수정하고 다시 검수해줘.

9. 최종 결과물
다음 파일을 제공해줘.
- 발표용 PDF(16:9): `<이름>.pdf`
- 슬라이드별 상세 발표 대본 DOCX: `<이름>_script.docx` (슬라이드 썸네일 포함)
- 수정할 수 있는 원본 HTML: `<이름>.html` (+ `pdf-design.css`)

최종 답변에는 다음 내용만 간단히 알려줘.
- 완성된 파일 경로 또는 링크
- 전체 슬라이드 수(본편/부록)
- 예상 발표 시간(`script` 결과)과 목표 시간
- 원본 자료에서 가져온 주요 Figure나 표
- 최종 검수 결과: `check` 오류·경고 건수, 직접 확인한 항목, 확인하지 못한 항목
