A cache-aside layer
cut read latency by 42%

Why it worked, how to reason about it, and where it stops working

Platform Ops Team · 2026-09
Based on: August Ops Report (sample)

먼저 알아야 할 배경지식

Cache-aside(캐시 어사이드)는 애플리케이션이 캐시를 먼저 조회하고, 없을 때만 DB를 읽은 뒤 캐시에 채워 넣는 방식입니다.

안녕하세요. 오늘은 8월에 도입한 캐시 계층이 읽기 지연을 어떻게 줄였는지, 그리고 그 효과를 식으로 어떻게 예측할 수 있는지 말씀드리겠습니다. 모든 수치는 예시 데이터입니다.

다음 슬라이드 연결

먼저 왜 캐시가 필요했는지부터 보겠습니다.

Reads, not writes, were saturating the database

Peak DB CPU hit 85% while most queries repeated the same keys.

  1. Read-heavy trafficMost API calls were product and profile lookups.
  2. Repeated keysThe same records were fetched again within minutes.
  3. Latency followed DB loadp95 rose whenever DB CPU peaked.
Source: August Ops Report (sample), Sec. 1 · DB CPU from monitoring dashboard

이 결과가 중요한 이유

인프라 증설 없이 목표를 달성했다는 점입니다.

Expected latency depends on the hit ratio, not on cache speed alone
$$ \mathbb{E}[T] = h\,t_c + (1-h)\,(t_c + t_{db}) = t_c + (1-h)\,t_{db} $$
\(h\)
Cache hit ratio (0–1)
\(t_c\)
Cache lookup time
\(t_{db}\)
DB read time on a miss
Standard cache latency model (simplified view) · values in Appendix are sample data

수식이 계산하는 것

요청 하나의 평균 읽기 지연입니다. p95가 아니라 평균이라는 점을 먼저 말합니다.

앞 항과 뒤 항의 의미

  • 앞 항 h·t_c: 캐시에 있을 때(확률 h) 캐시 조회 시간만 든다.
  • 뒤 항 (1−h)(t_c + t_db): 캐시에 없을 때 캐시를 먼저 보고 DB까지 읽는다.

단계별 유도

  1. 기대값 = Σ(경우의 확률 × 그 경우의 시간)에서 출발합니다.
  2. 두 항을 전개하면 h·t_c + t_c − h·t_c + (1−h)·t_db 입니다.
  3. h·t_c가 상쇄되어 t_c + (1−h)·t_db 가 남습니다.

이 식은 캐시를 붙였을 때 평균 읽기 지연을 계산합니다. 캐시에 있으면 캐시만 보고, 없으면 캐시를 본 뒤 DB까지 읽는다는 두 경우를 확률로 더한 것입니다.

정리하면 오른쪽처럼 됩니다. 캐시 조회 시간은 항상 들고, DB 시간은 캐시에 없을 때만 듭니다. 그래서 효과를 좌우하는 것은 캐시 속도보다 적중률 h입니다.

헷갈리기 쉬운 점

이 식은 평균만 설명합니다. p95 개선은 이 식에서 바로 나오지 않으므로 Figure 수치와 섞어 말하지 않습니다.

The read path checks the cache first and fills it on a miss
  1. Request keyAPI receives a read for key k
  2. Look up cacheGET k from Redis
  3. Hit or missif value ≠ null return it immediately
  4. On a missRead DB, SET k with TTL, return
Cache-aside read path (simplified view) · TTL policy in August Ops Report (sample), Sec. 2

입력·반복·조건·출력

  • 입력: 조회할 키 k
  • 조건: 캐시 값이 있으면 바로 반환(적중), 없으면 DB 조회(미적중)
  • 출력: 값, 그리고 미적중이었다면 캐시에 새로 채워진 항목

작은 예시

상품 42번을 처음 읽으면 미적중 → DB에서 읽고 캐시에 저장. 1분 뒤 같은 요청은 적중 → 캐시에서 바로 반환.

읽기 경로는 네 단계입니다. 캐시를 먼저 보고, 있으면 바로 돌려줍니다. 없을 때만 DB를 읽고, 다음 요청을 위해 캐시에 채워 둡니다. TTL은 캐시 항목의 유효기간입니다.

같은 피크 시간대를 비교한 월평균입니다. p95는 221에서 128밀리초로 42퍼센트 줄었고, DB CPU는 85에서 41퍼센트로 떨어졌습니다. 적중률은 월말 기준 88퍼센트입니다.

주의점

장애 건수 감소는 캐시만의 효과라고 원본에서 단정하지 않았습니다. 인과관계로 말하지 않습니다.

Cache-aside fit a read-heavy API better than write-through

Cache-aside (chosen)

  • Caches only keys that are actually read
  • DB stays the source of truth
  • First read of a key is a miss

Write-through

  • Every write also updates the cache
  • Fresh data on first read
  • Caches keys that may never be read
For read-heavy traffic with repeated keys, caching on demand used less memory for the same hit ratio.
Source: August Ops Report (sample), Sec. 2 design notes

두 방식을 비교하면, 우리 트래픽은 읽기가 많고 같은 키가 반복되기 때문에 실제로 읽히는 키만 캐시에 올리는 cache-aside가 메모리 대비 효율이 좋았습니다.

헷갈리기 쉬운 점

write-through가 나쁜 방식이라는 뜻이 아닙니다. 첫 읽기부터 최신 값이 중요한 서비스에서는 더 적합할 수 있습니다.

Where the gain stops

Conditions and limits of the result

이제 이 결과가 어디까지 유효한지 보겠습니다.

The result holds only while keys repeat and data can be slightly stale
  • Batch jobs read unique keys, so they barely hit the cache.
  • Price changes can be stale until the TTL expires.
  • A cold cache after restart temporarily brings back DB load.

By the model on slide 4, if the hit ratio fell back toward 70%, the mean latency gain would shrink by roughly half. This is our projection, not a measured result.

Source: August Ops Report (sample), Sec. 4 · projection is presenter's calculation

주의점

오른쪽 점선 박스는 원본 결과가 아니라 4번 슬라이드 식으로 계산한 발표자 추정입니다. 말할 때도 “제 계산으로는”이라고 구분합니다.

이 효과에는 조건이 있습니다. 같은 키가 반복되어야 하고, 약간 오래된 데이터를 허용할 수 있어야 합니다. 배치 작업처럼 매번 다른 키를 읽으면 캐시가 거의 도움이 되지 않습니다.

제 계산으로는 적중률이 70퍼센트 수준으로 떨어지면 평균 지연 개선 폭이 절반 정도로 줄어듭니다. 계산 과정은 부록에 있습니다.

Plugging in sample values shows why the hit ratio dominates
$$ \mathbb{E}[T] = t_c + (1-h)\,t_{db}, \quad t_c = 2\,\text{ms},\; t_{db} = 40\,\text{ms} $$
  1. \(h = 0.88\): \(2 + 0.12 \times 40 = 6.8\) msAugust hit ratio (sample)
  2. \(h = 0.71\): \(2 + 0.29 \times 40 = 13.6\) msFirst week after rollout (sample)
  3. \(h = 0\): \(2 + 40 = 42\) msNo hits: slightly slower than no cache (40 ms)
Presenter's calculation with sample timings · model from slide 4

숫자 예시

캐시 조회 2ms, DB 조회 40ms로 두고 적중률만 바꿔 계산합니다.

적중률이 0.88이면 평균 6.8밀리초, 0.71이면 13.6밀리초로 두 배가 됩니다. 적중률이 0이면 오히려 캐시가 없을 때보다 2밀리초 느립니다. 그래서 캐시 성능보다 적중률 관리가 중요합니다.
