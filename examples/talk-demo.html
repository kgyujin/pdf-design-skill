Expected latency depends on the hit ratio, not on cache speed alone
$$ \mathbb{E}[T] = h\,t_c + (1-h)\,(t_c + t_{db}) = t_c + (1-h)\,t_{db} $$
\(h\)
Cache hit ratio (0–1)
\(t_c\)
Cache lookup time
\(t_{db}\)
DB read time on a miss
The read path checks the cache first and fills it on a miss
  1. Request keyAPI receives a read for key k
  2. Look up cacheGET k from Redis
  3. Hit or missif value ≠ null return it immediately
  4. On a missRead DB, SET k with TTL, return

Cache-aside fit a read-heavy API better than write-through

Cache-aside (chosen)

  • Caches only keys that are actually read
  • DB stays the source of truth
  • First read of a key is a miss

Write-through

  • Every write also updates the cache
  • Fresh data on first read
  • Caches keys that may never be read
For read-heavy traffic with repeated keys, caching on demand used less memory for the same hit ratio.

Where the gain stops

Conditions and limits of the result

The result holds only while keys repeat and data can be slightly stale
  • Batch jobs read unique keys, so they barely hit the cache.
  • Price changes can be stale until the TTL expires.
  • A cold cache after restart temporarily brings back DB load.

By the model on slide 4, if the hit ratio fell back toward 70%, the mean latency gain would shrink by roughly half. This is our projection, not a measured result.

Plugging in sample values shows why the hit ratio dominates
$$ \mathbb{E}[T] = t_c + (1-h)\,t_{db}, \quad t_c = 2\,\text{ms},\; t_{db} = 40\,\text{ms} $$
  1. \(h = 0.88\): \(2 + 0.12 \times 40 = 6.8\) msAugust hit ratio (sample)
  2. \(h = 0.71\): \(2 + 0.29 \times 40 = 13.6\) msFirst week after rollout (sample)
  3. \(h = 0\): \(2 + 40 = 42\) msNo hits: slightly slower than no cache (40 ms)
